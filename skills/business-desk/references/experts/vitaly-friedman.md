## Methods

### Choose patterns according to the customer task

Original research status: supported.

Start with the goal and content, then select and adapt interaction patterns. A configurator, comparison table, or booking calendar is conditional on a real customer need.

* [Designing a Perfect Configurator UX](https://www.smashingmagazine.com/2018/02/designing-a-perfect-responsive-configurator/). Author: Vitaly Friedman. Locator: What Problem Are We Solving?. Validate whether customization serves the customer before building a configurator. Match the depth of choices to the task, use useful presets, and present actual product information. Selected sections discuss car examples and responsive decisions. The author explicitly cannot establish a conversion uplift from the observed engagement. This does not teach a live dealership inventory feed.
* [Smart Responsive Design Patterns](https://www.smashingmagazine.com/2016/05/smart-responsive-design-patterns-or-when-off-canvas-isnt-good-enough/). Author: Vitaly Friedman. Locator: Responsive Complexity Graph. Adapt patterns to context rather than transplanting them unchanged. Start complex components with their content and core purpose, then prototype how the experience changes across screen sizes. The article uses a hypothetical BMW task. Stable design reasoning is retained; old browser and code details are not assumed current.
* [Designing the Perfect Feature Comparison Table](https://www.smashingmagazine.com/2017/08/designing-perfect-feature-comparison-table/). Author: Vitaly Friedman. Locator: When Is A Feature Comparison Useful?. Comparison is useful when customers need to evaluate consequential alternatives. It may add little value to routine purchases. Emphasize attributes that customers understand and care about, backed by consistent real product data. Missing attributes can undermine decisions. Selected sections were inspected, not every implementation example in this long article.

### Preserve filtering context and show useful feedback

Original research status: candidate.

Retain selections and avoid unexpected layout movement. Show result counts and loading or empty states appropriate to the implementation.
